## 1. Как читать этот документ

Проект начинался под документ v1.4 — развёрнутую enterprise-интерпретацию задания.
После получения оригинального PDF Газпромбанк.Тех выяснилось, что это **хакатон с
жюри и live-защитой**, а не промышленное внедрение. Часть построенного попадает в
цель, часть оказалась преждевременной, а главное — **единственная объективная метрика
оценки (точность ≥80%) не закрыта вообще**.

Ниже: фактическое состояние, разрыв по каждому acceptance criterion и порядок работ.

## 3. Разрыв по acceptance criteria

Статусы получены прямой проверкой репозитория и запуском кода, а не по памяти.

| ID | Критерий | Статус | Чем подтверждено / что осталось |
|---|---|---|---|
| **AC-01** | ML-модель, порог ≥80% | **частично** | групповой nested CV и negative-source audit реализованы; нет экспертно подтверждённых корпусных негативов |
| **AC-02** | Объяснение признаков решения | **готово** | вклад признаков через коэффициенты линейной модели, `signal_classifier.py:146` |
| **AC-03** | Открытый запрос не ограничен 100 технологиями | **частично** | непокрытый запрос запускает ограниченный поиск по источникам с разрешённой аналитикой; candidates остаются вне канонической онтологии, а discovery index не является ML confidence |
| **AC-04** | TOP-15 с confidence | **частично** | калибровка и Brier/ECE-отчёт реализованы; нужна проверка на экспертно подтверждённых негативах |
| **AC-05** | Русская аналитическая выдача | **частично** | карточка может быть сгенерирована по-русски и помечена; source-ID/числовая проверка не доказывает смысловую точность, нужен доступный LLM и оценка качества/latency |
| **AC-06** | Источник: name/url/date/type/language/trust | **частично** | миграция, API metadata и single-source gate добавлены; миграция и scoring пока не проверены на доступной БД |
| **AC-07** | Фильтрация зрелости, хайпа, шума | **готово** | `scoring/filters.py`: три правила, причина на русском, применяются после ML |
| **AC-08** | Счётчик сигналов с confidence >75% | **готово** | `GET /api/v1/signals/stats` |
| **AC-09** | Docker + README + dependencies | **готово** | `Dockerfile`, `frontend/Dockerfile`, `docker-compose.yml` с healthcheck |
| **AC-10** | Web demo для жюри | **готово** | Next.js работает |
| **AC-11** | Презентация ≤15 слайдов | **не начато** | к защите |

**Готово 5, частично 5, не выполнено 1.**

### Почему AC-01 остаётся «частично»

Предыдущая accuracy 0.967 пришла из одиночного разбиения 100 положительных
экспертных примеров и 18 вручную составленных seed-негативов. Она не была
защитимой метрикой. Теперь есть grouped nested CV, OOF-калибровка, confusion
matrix, PR-AUC (average precision), Brier/ECE и feature ablations. Повторный
smoke test на тех же illustrative seeds дал accuracy 0.9915, но source-only
проверка достигла AP 0.9985, а rationale-only — AP 0.9984. Почти идеальное
разделение показывает разницу в источниках и стиле разметки, а не качество
production-модели. Эти числа не закрывают порог хакатона.

Также устранено несоответствие входов: по умолчанию модель не использует
свободный rationale, служебный domain или число ссылок. Для corpus-кандидатов
добавлены проверяемые provenance, snapshot cutoff и `pending` review state;
тренер принимает только явно одобренные экспертами записи.

Осталось для закрытия AC-01:

1. Подключить snapshot БД и выгрузить кандидатов из того же корпуса.
2. Провести экспертную проверку, устранить пересечения и собрать сопоставимый
   контролируемый negative set.
3. Перезапустить grouped evaluation и подтвердить качество на независимо
   отложенных экспертных данных. До этого 80% не заявлять.

## 4. P0 — блок ML-модели (AC-01, AC-02, AC-08)

Единственная объективная метрика хакатона. Протокол проверки реализован, но
разметка и корпусные данные пока не позволяют подтвердить качество.

### 4.1. Аудит датасета

- Связь между стадией развития, трендом упоминаний и баллом.
- Дубликаты и почти-дубликаты технологий.
- Leakage audit: не утекает ли `Балл` через текстовое обоснование.
- Распределения признаков по шести областям.

### 4.2. Фиксация target

Решение принимается **до** подбора модели и не меняется после просмотра validation.
Варианты:

1. Бинарный: сигнал / не сигнал (нужен negative set).
2. Ordinal по баллу 3–7 + отдельное правило перевода в signal/non-signal.
3. Регрессия балла + порог.

Датасет содержит **только положительные примеры** — без решения по негативу
бинарная постановка невозможна.

### 4.3. Протокол отрицательных примеров

Самая рискованная часть: лёгкий негатив даёт завышенную метрику, и 80% перестают
что-либо доказывать.

| Класс негатива | Как строить | Проверка |
|---|---|---|
| Зрелые технологии | высокий объём + низкое ускорение + высокая maturity из собственного корпуса | должны быть реально зрелыми, а не просто известными |
| Маркетинговый хайп | высокий early warning при низком confirmed | механизм уже заложен в схеме v1.5 |
| Информационный шум | малый объём, низкая coherence, нет cross-source | не должен быть тривиально отделим |

Негатив строится **из того же корпуса**, а не из выдуманного списка. Отдельный
аудит: если модель отличает негатив по одним словам — метрика недействительна.

### 4.4. Модели и валидация

- Baseline: Logistic Regression — контрольная точка и прямая интерпретируемость.
- Дерево: Random Forest / Gradient Boosting.
- Основной кандидат: XGBoost по табличным признакам.
- Текст: multilingual embeddings (модель уже установлена).
- Обязательно: cross-validation, hold-out, ablation по группам признаков,
  калибровка, confusion matrix, PR-AUC, error analysis.

### 4.5. Интерпретация

SHAP для бустинга либо коэффициенты для линейной модели. В выдаче — 3–6 ключевых
факторов с направлением вклада, а не только итоговый процент.

## 5. P0 — открытый поиск без онтологии (AC-03)

Запрос, покрытый `data/ontology/ai_pilot.json`, по-прежнему использует рассчитанный
snapshot. Для непокрытого запроса добавлен асинхронный поиск через подключённые
OpenAlex, arXiv, GitHub и GDELT; выбираются только включённые источники с
`approved` license status и разрешённой derivative analytics. Извлекатель строит
предложения по названиям и темам документов, объединяет точные и консервативно
похожие варианты, сохраняет ссылки и происхождение, а UI опрашивает задачу и
показывает результаты.

Это **частичная**, не закрытая реализация AC-03:

1. Discovery index — прозрачная эвристика, не вероятность и не production ML score.
2. Текущее объединение работает по строкам и символьному TF-IDF; embeddings,
   временной рост и сквозная scoring pipeline ещё не подключены.
3. Результаты сохраняются в прогрессе задачи для просмотра, но не материализуются
   в `CandidateTechnology`/`ClusterRun`; экспертное promotion API и lineage для
   таких кандидатов не реализованы.
4. News-only и недостаточно разнообразные кандидаты остаются pending review;
   автоматическое создание/изменение канонической `Technology` запрещено.

## 6. P0 — русскоязычная выдача (AC-05)

Требование явное: аналитика на русском, для зарубежных источников — русское резюме
с сохранением оригинального названия, ссылки, даты и языка.

Карточка тренда теперь может быть собрана `LlmCardGenerator` с явным требованием
русского текста. Перед выдачей она проходит тот же source-ID/metric verifier, что
и детерминированная карточка. Если модель недоступна, вывод остаётся на языке
исходных данных; API и UI явно отмечают fallback. Вызов ограничен одной попыткой
и 70 секундами.

Текущий verifier проверяет ссылки на документы и числовые значения, но не
семантическое следование текста источникам; автоматически составленный пересказ
нужно сверять с оригиналами.

Тексты документов и заголовки не переводятся на месте и остаются основанием для
ClaimVerifier. Добавлены отдельные nullable-поля `summary_ru` и
`summary_model_version`, `original_title` и generated-summary marker; для
документных резюме пока нет генератора и записи в БД. Нужно проверить качество,
задержку и source-faithfulness на реальных материалах и решить, нужен ли отдельный
асинхронный summary job.

## 8. P1 — метаданные источников (AC-06)

Миграция добавляет `Source.trust_level`/`trust_reason` и у `Document` — тип
документа, язык оригинала, `retrieved_at`, `original_title`, а также отдельные
поля под generated summary. API выдаёт эти значения вместе с source family,
датой публикации, URL и mapping provenance.

Scoring теперь исключает технологию с единственным семейством источников и
доказательную базу только из источников с низким/неизвестным доверием; причины
сохраняются в статусе. `companies` не помечается слабым автоматически: доверие
задаётся явно для конкретного источника. Код и pure policy tests готовы; миграция,
seed-значения и scoring запрос требуют проверки на доступной БД.

## 9. Фильтры хайпа и шума (AC-07) — готово

`scoring/filters.py`, функция `assess_candidate`. Правила применяются **после**
ML-оценки: модель отвечает, насколько кандидат похож на обученные сигналы, но не
отменяет проверяемых продуктовых ограничений.

- **Maturity:** стадия Mainstream/Mature → исключение.
- **Hype:** высокий рыночный сигнал (≥70) при слабом независимом подтверждении (<35) → пометка.
- **Noise:** недостаток объёма и независимых источников.

Каждое решение возвращает `status` и `reason` на русском — это и есть материал для
пунктов 7–8 demo-сценария.

## 10. Известные дефекты методологии

Найдены при работе с реальными данными, исправления внесены, но **каждый меняет
методику расчёта и требует согласования**. Подробно — в [limitations.md](limitations.md).

1. Формула growth §24.4 с `eps=1` не защищает от малых выборок: рост 0 → 3 документа даёт больший балл, чем 3 000 → 10 000.
2. Задержка индексации читается как спад активности.
3. Правило «missing ≠ zero» не покрывало пропущенные периоды внутри окна.
4. §9 не различает факт из источника и рассчитанный показатель.
5. Перераспределение весов ломает порог auto-accept при малом покрытии сигналов.
6. Шум GDELT: 77% выдачи по фразовому запросу не по теме.
7. 25% веса ETS не поддаётся историческому бэктесту с холодного старта.
8. `PRIMARY KEY` из §32.1 нереализуем в PostgreSQL.

## 11. Что отложено осознанно

Сильные идеи, не влияющие на критерии хакатона:

- Автоматическое расширение онтологии через HDBSCAN/BERTopic (P2).
- Ансамбль специализированных детекторов.
- Bayesian change-point detection.
- Learning-to-Rank после накопления разметки.
- Многоязыковая асимметрия как отдельный сигнал.
- Подключение EPO, CORDIS, PatentsView.
- Пять экранов экспертного ревью, существующих только в API.

## 12. Порядок работ

| | Работа | Критерий |
|---|---|---|
| 1 | Выгрузка кандидатов из корпуса + expert review | код готов; нужен DB snapshot и разметка |
| 2 | Grouped nested CV, ablation, калибровка, PR-AUC | протокол готов; нужны подтверждённые labels |
| 3 | Ограниченный открытый поиск и review-only извлечение кандидатов; embeddings, scoring и candidate review остаются | AC-03, частично |
| 4 | Русская карточка с верификацией оригинальных источников; сохранённые summaries ещё не генерируются | AC-05, частично |
| 5 | Метаданные источников и single-source gate; нужна проверка миграции/scoring на БД | AC-06, частично |
| 6 | Презентация | AC-11 |

Шаги 1–2 — критический путь: текущий smoke test с 18 illustrative negatives
показывает почти идеальное разделение даже по одному shortcut-признаку. До
проверки на reviewed corpus candidates ни одна accuracy не защищаема перед жюри.
