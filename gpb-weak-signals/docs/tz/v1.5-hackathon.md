## 0. Назначение версии 1.5

Версия 1.5 переориентирует проект с enterprise-платформы длительного мониторинга
на хакатонное решение, где приоритет — доказательство технической способности
обнаруживать слабые сигналы, прозрачность методологии и работоспособный открытый поиск.

- Сначала доказать качество модели на предоставленном датасете и зафиксировать честную схему валидации.
- Не ограничивать открытый поиск стартовым перечнем из 100 технологий.
- Сделать объяснение решения частью результата, а не постфактум сформированным текстом.
- Показать исключение зрелых технологий, маркетингового хайпа и информационного шума.
- Минимизировать инфраструктурный обвес, не влияющий на критерии хакатона.

## 1. Основания и требования организаторов

Исходное ТЗ описывает два взаимосвязанных этапа: обучение модели на предоставленном
датасете и открытый поиск по внешним источникам. Финальная демонстрация выполняется
в реальном времени.

- Точность модели: порог 75–80%; в данной версии принимается целевой порог **80%**.
- Модель должна быть **интерпретируемой**: показывать признаки, по которым наблюдение признано слабым сигналом.
- Открытый поиск **не ограничен** предоставленным датасетом или заранее заданным перечнем технологий.
- Для каждого источника: название, ссылка, дата публикации, тип источника, язык оригинала, уровень доверенности.
- Итоговая аналитика — **на русском**; для зарубежных источников требуется русское резюме с сохранением оригинального названия и метаданных.
- Необходимо отделять слабые сигналы от зрелых технологий, массового внедрения, отраслевых стандартов, маркетингового хайпа и информационного шума.
- Поставка: репозиторий, Docker, README, зависимости, техническая документация, web-стенд, презентация ≤15 слайдов.

## 2. Датасет обучения

| Характеристика | Значение |
|---|---|
| Количество записей | 100 |
| Областей | 6 |
| Области | Индустриальный ИИ — 17; Роботы — 17; Инфраструктура ИИ — 17; Финтех — 17; Защита ИИ — 16; Edge — 16 |
| Диапазон балла | 3–7 |
| Распределение баллов | 3: 7 · 4: 22 · 5: 28 · 6: 28 · 7: 15 |
| Уникальных технологий | 100 |

Поля записи: технология, область, компании, обоснование слабого сигнала, стадия
развития, тренд упоминаний, балл, источники.

> **Критическое ограничение.** В наборе отсутствует явный negative-класс. Target
> нельзя автоматически трактовать как бинарный label без отдельного решения.

## 3. Target и стратегия обучения

### 3.1. Правило выбора target

1. Провести аудит структуры XLSX, проверить связь между стадией, трендом упоминаний и баллом.
2. Зафиксировать target **до** финального подбора модели и не менять после просмотра validation.
3. Бинарная проверка организаторов → бинарный классификатор. Проверка по экспертному баллу → ordinal/regression + отдельное правило перевода в signal/non-signal.
4. Все преобразования target и пороги документировать в README и отчёте.

### 3.2. Отрицательные примеры

| Источник негатива | Логика | Риск смещения |
|---|---|---|
| Зрелые технологии | Высокий объём/внедрение + низкое ускорение + высокая зрелость | Модель научится отличать известные слова, а не слабость сигнала |
| Маркетинговый хайп | Высокое раннее внимание при слабом независимом подтверждении | Нельзя путать отсутствие данных с отсутствием технологии |
| Информационный шум | Малый объём + низкая coherence + нет cross-source подтверждения | Слишком лёгкий негатив даст завышенную метрику |

**Правило:** negative set строится из того же или сопоставимого корпуса и проходит
отдельный аудит. Только очевидные негативы делают 80% accuracy неубедительными.

### 3.3. Базовые модели

- Baseline 1: Logistic Regression — контрольная точка и интерпретируемость.
- Baseline 2: Random Forest / Gradient Boosting.
- Основной кандидат: XGBoost/градиентный бустинг по табличным признакам.
- Текстовые признаки: multilingual embeddings + агрегаты по источникам.
- LLM — для русскоязычного объяснения и структурирования evidence, **не** как единственный источник решения.

## 4. Feature Engineering

| Группа | Примеры признаков | Роль |
|---|---|---|
| Новизна | возраст, semantic distance до известных технологий | отделение нового от давно известного |
| Динамика | growth, acceleration, slope, change-point | раннее обнаружение ускорения |
| Научный сигнал | публикации, авторы, организации, preprints | исследовательская активность |
| IP | патентные семьи, applicants, CPC/IPC diversity | технологическая/правовая активность |
| Adoption | GitHub, HF, PyPI/npm, contributors, releases | раннее внедрение |
| Cross-source | число независимых типов источников | защита от единичного вброса |
| Maturity | стадия, признаки массового внедрения, saturation | отсечение зрелых технологий |
| Trust | тип источника, доверенность, независимость | контроль качества evidence |
| Author mobility | переход авторов между областями | опережающий сигнал новой области |

## 5. Интерпретируемый скоринг

```
Signal probability = f(novelty, growth, acceleration, research, adoption,
                       cross_source, maturity_inverse, source_trust)
```

Пример объяснения:

```
Уверенность модели: 86%
 + высокая динамика упоминаний
 + ранняя стадия
 + рост числа независимых источников
 + появление практических реализаций
 − слабое патентное подтверждение
```

Для деревьев/бустинга — SHAP или эквивалент. Для линейного baseline — коэффициенты.
В UI показывать не только итоговый процент, но и 3–6 ключевых факторов.

## 6. Защита от хайпа, зрелости и шума

Фильтр — самостоятельный этап перед финальным TOP-15.

- **Maturity filter:** штраф/исключение при признаках массового внедрения, сформированного рынка, устойчивых лидеров.
- **Hype filter:** высокий media/early score при низком independent confirmation → «возможный хайп / требуется подтверждение».
- **Noise filter:** малый объём, низкая coherence, нет независимых источников → исключение.
- **Single-source rule:** корпоративный блог, пресс-релиз, соцсеть или агрегатор не могут быть единственным основанием.
- Каждое исключение логируется: `candidate → filter → reason`.

## 7. Early Warning и Confirmed Emerging

| Контур | Источники/сигналы | Назначение |
|---|---|---|
| Early Warning | GitHub events, HF, PyPI/npm, новости/HN/Reddit, быстрые публикации | Что начало двигаться |
| Confirmed Emerging | научные публикации, патенты, R&D, независимые источники | Что получает независимое подтверждение |

`Delta = Early Warning − Confirmed Emerging`. Высокая положительная delta не означает,
что технология плохая — это может быть раннее обнаружение. Но кандидат должен быть
явно помечен как недостаточно подтверждённый.

## 8. Открытый поиск

```
Запрос пользователя
  → поиск по открытым источникам
  → извлечение technology candidates
  → нормализация / semantic deduplication
  → feature engineering
  → ML inference
  → maturity / hype / noise filters
  → ranking
  → TOP-15
  → русскоязычная аналитическая карточка + evidence
```

Discovery через HDBSCAN/BERTopic — желательное расширение, **не P0**. Для MVP
достаточно устойчивого извлечения и семантического объединения кандидатов.

## 10. Метаданные источника

```

trust_level, trust_reason, retrieved_at, evidence_text,
```

## 12. Persistent corpus и режим работы

Компромисс для хакатона: предварительно собранный cache/corpus для демонстрации +
live fallback при отсутствии актуальных данных. Новые кандидаты обрабатываются
асинхронно, если полный анализ занимает больше времени. Enterprise-механизмы
оркестрации и lineage не должны блокировать MVP.

## 13. Валидация и доказательство качества

| Эксперимент | Что проверяем |
|---|---|
| Cross-validation на train | устойчивость модели и способность разделять классы |
| Hold-out / validation | контрольная оценка до финальной защиты |
| Ablation | какие группы признаков реально дают прирост |
| Negative-source audit | не завышена ли метрика из-за лёгких негативов |
| Calibration | соответствует ли 80% confidence реальной вероятности |
| Error analysis | какие зрелые/хайповые/шумовые случаи модель путает |

Метрики: Precision, Recall, F1, accuracy. При дисбалансе — обязательно confusion
matrix и PR-AUC. Финальный отчёт — один зафиксированный эксперимент без подгонки.

## 15. Demo-сценарий

1. Ввести заданное жюри направление, например «технологии в ИИ».
2. Показать количество обработанных источников и кандидатов.
3. Сформировать TOP-15.
4. Открыть 2–3 наиболее сильных сигнала.
5. Для каждого: проблема → преимущество → стадия → confidence → ключевые признаки → источники.
6. Открыть источник и показать проверяемость первоисточника.
7. Показать зрелую технологию, которая была отфильтрована, и объяснить почему.
8. Показать хайповый/шумовой кандидат и причину понижения или исключения.
9. Показать, что зарубежные источники представлены с русским резюме и оригинальными метаданными.

## 19. Итоговый контракт MVP

Система принимает свободный технологический запрос, получает данные из открытых
источников, выделяет кандидатов, рассчитывает вероятность слабого сигнала на основе
обученной и интерпретируемой модели, фильтрует зрелые технологии/хайп/шум, формирует
TOP-15 и для каждого результата показывает русскоязычное объяснение и проверяемые
источники.

**Главный критерий технической готовности:** воспроизводимый эксперимент с
зафиксированным target, контролируемой валидацией и достижением целевого порога
качества, после чего тот же inference pipeline используется в открытом demo-сценарии.
