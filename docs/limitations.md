# Расхождения с ТЗ и ограничения реализации

Документ фиксирует места, где реализация отходит от ТЗ v1.4 или где
требование ТЗ невыполнимо в заявленном виде. Каждый пункт — кандидат в
повестку обсуждения с заказчиком.

---

## 1. Point-in-time для изменяемых метрик выполним частично

**ТЗ:** §29.3 + ADR-008 требуют, чтобы score на дату T использовал только
данные, доступные на T. §34 строит на этом rolling-origin backtesting.

**Проблема:** цитирования, звёзды, контрибьюторы и загрузки — изменяемые
величины. Внешние API отдают только сегодняшнее значение. Число цитирований
статьи по состоянию на 2021 год восстановить из OpenAlex нельзя: его там
просто нет.

**Следствие для §34.** Честному бэктестингу на исторических cut-off сразу
поддаются признаки на неизменяемых датах:

| Признак | Бэктестинг с нуля | Почему |
|---|---|---|
| Novelty | да | даты публикации/priority неизменны |
| Growth, Acceleration | да | считаются по объёмам публикаций |
| Research Momentum | да | то же |
| Patent Momentum | да | `priority_date` неизменна |
| Cross-domain | да | производная от объёмов |
| **Citation Momentum** | **нет** | исторических срезов цитирований нет |
| **Adoption Momentum** | **частично** | восстановимо из GH Archive (события датированы), но не из GitHub API |
| Market Momentum | нет | зависит от новостных/компанейских источников |

Суммарный вес невалидируемых сразу признаков — 0.07 + 0.08 + 0.10 = **0.25**
от ETS.

**Что сделано:** таблица `document_metric_snapshots` пишет значения с
`observed_at` с первого дня, чтобы через 12–18 месяцев бэктестинг стал
возможен. Флаг `is_reconstructed` отличает значения, восстановленные из
событийных дампов, от снятых с живого API.

**Что требует решения заказчика:** признать эти три признака
неваллидируемыми на старте — или заложить работу по историческим дампам
(GH Archive для adoption, датированные дампы Semantic Scholar для цитирований).

## 2. Формула growth §24.4 не защищает от малых выборок

**ТЗ:** §24.4 задаёт `growth = ln((V_t + eps) / (V_t-k + eps))`, eps = 1.
§24.18 требует «не считать трендом одиночный всплеск из 1–2 документов».

**Проблема:** eps = 1 этого не обеспечивает. Фактические значения:

```
    0 →     3 документа   growth = 1.386
 3000 → 10000 документов  growth = 1.204
```

Кластер из трёх документов получает более сильный сигнал роста, чем
реальный рост на семь тысяч публикаций. Единственная защита в ТЗ —
бинарный порог `MIN_ACTIVITY` на этапе отбора (§24.20), который не
исправляет искажение ранжирования среди кандидатов, порог прошедших.

**Что сделано:** добавлена усадка `n / (n + k)` (`volume_shrinkage`,
k = 5 по умолчанию). После неё 0 → 3 даёт 0.52 против 1.20 у большого
роста. Параметр конфигурируем, входит в `scoring_version` и подлежит
калибровке отдельно от весов ETS.

**Статус:** дополнение к ТЗ, требует согласования как часть методологии.

## 3. Полоса human review не имеет правила по умолчанию

**ТЗ:** §24.21 отправляет маппинги со score 0.65–0.85 на экспертное ревью.
Поведение для непросмотренных не задано.

**Проблема:** на корпусе в сотни тысяч документов даже 5 % в этой полосе —
тысячи элементов. Если они учитываются наравне с подтверждёнными, ревью
декоративно. Если не учитываются — покрытие технологии зависит от того,
сколько эксперт успел посмотреть, и меняется непредсказуемо между
запусками.

**Что сделано:** параметр `unreviewed_review_band_weight` (0.5 по
умолчанию) — непросмотренный маппинг учитывается с половинным весом и
снижает `evidence_confidence`. Поле `review_deadline_at` позволяет
отслеживать возраст очереди.

**Что требует решения заказчика:** подтвердить правило и оценить
пропускную способность экспертов — от неё зависит размер полосы, который
система может себе позволить.

## 4. `PRIMARY KEY` из §32.1 нереализуем в PostgreSQL

**ТЗ:** §32.1 объявляет
`cluster_memberships(... PRIMARY KEY(cluster_run_id, cluster_id, COALESCE(technology_id, document_id)))`.

**Проблема:** PostgreSQL не поддерживает первичный ключ по выражению.

**Что сделано:** суррогатный `id UUID PK` + два частичных уникальных
индекса + `CHECK`, что заполнено ровно одно из двух полей. Гарантия
эквивалентна заявленной.

---

## 5. Счётчики байтов не помещаются в INTEGER

Порог EPO OPS — 4 ГБ/неделя = 4 294 967 296 байт, что превышает диапазон
`INTEGER` (2 147 483 647). `weekly_volume_cap_bytes` и `bytes_transferred`
переведены в `BIGINT`. Мелочь, но обнаруживается только при первой попытке
записать реальный порог.

## 6. Патентный слой пилота — USPTO, не EPO

EPO OPS в §30 имеет статус BLOCKED. Для пилота используется PatentsView
(USPTO): открытый bulk-доступ, содержит `priority_date` и CPC, то есть
Patent Momentum и патентная часть Novelty считаются на реальных данных.

**Ограничение:** покрытие американское. Европейские и российские заявки,
не имеющие параллельной подачи в США, в пилоте не видны. Для оценки
методологии этого достаточно; для production-выводов о географии — нет.

## 7. Правая цензура: задержка индексации читается как спад

**ТЗ:** §29.3 описывает левую цензуру — отсутствие данных до
`coverage_start_date`. Правая цензура не упомянута нигде, а §24.4/24.5
считают growth и acceleration окнами, заканчивающимися на дате расчёта.

**Проблема:** свежие публикации ещё не проиндексированы источником.
Замер на пилотном корпусе (OpenAlex, `as_of` = 2026-09-13):

| месяц | публикаций |
|---|---|
| 2026-01 | 28 |
| 2026-02 | 12 |
| 2026-03 | 6 |
| 2026-04 | 4 |
| 2026-07 | 3 |
| 2026-08 | 1 |

Это не спад активности — это хвост индексации. Окно динамики читает его
как обвал, и штраф получают именно быстрорастущие технологии, ради которых
система и строится.

**Эффект измерен.** До правки Agentic AI занимал 12-е место из 13 на
корпусе, целиком собранном по запросу «agentic AI», с growth = 8.3. После
исключения последних 6 месяцев — 9-е место, growth = 75.0.

**Что сделано:** параметр `indexing_lag_months` (6 по умолчанию); все окна
заканчиваются на `effective_end`, а не на `as_of_date`.

**Что требует решения:** значение должно оцениваться эмпирически по
каждому источнику — сравнением числа документов за один и тот же месяц в
последовательных снапшотах. 6 — стартовая оценка, а не измеренная величина.

## 8. Peer group пилота не является peer group

**ТЗ:** §29.4 (ADR-004) требует нормализовать внутри versioned peer group
из внешней таксономии и явно запрещает считать percentile по 30–50
кандидатам.

**Состояние пилота:** популяция — 13 технологий, все из области ИИ, все
выведенные из корпуса по одному запросу. Это нарушает оба условия:
популяция меньше минимума (30) и не является внешней таксономией.

**Следствие:** абсолютные значения баллов в пилоте показательны только как
демонстрация работы конвейера. Ранжирование внутри такой популяции
неустойчиво — перестановка двух технологий двигает балл на единицы пунктов.
Система об этом сообщает: в лог пишется `small_reference_population`, а
размер популяции сохраняется в `trend_scores.reference_population_size`.

**Что нужно для осмысленных чисел:** загрузить peer groups из OpenAlex
Field/Subfield и CPC, расширить корпус за пределы одного запроса.

## 9. Порог confidence отсекает весь пилотный результат — и это правильно

При двух подключённых семействах источников из семи (research +
open_source) `evidence_confidence` всех 13 технологий оказывается в
диапазоне 7–37 при пороге 60 (§24.24). Ни одна технология не проходит
фильтры §24.20, и TOP-15 не формируется.

Это не дефект, а заявленное поведение: система отказывается публиковать
рейтинг, который не может обосновать. Подключение патентов, R&D и
новостей поднимает `source_diversity` и снимает штраф за недостающие
признаки (сейчас 0.48 веса ETS приходится на недоступные сигналы).

Для демонстрации CLI печатает полное ранжирование с пометкой, кто прошёл
порог, вместо пустой выдачи.

## 10. `--limit` на хронологическом backfill обрезает свежий конец ряда

**Обнаружено на пилоте.** Коннекторы GitHub и GDELT обходят историю
нарезкой по интервалам дат от старых к новым. Параметр `--limit`
останавливает загрузку по числу записей — то есть отсекает **последние**
месяцы, а не первые.

Фактический охват после загрузки с `--limit`:

| источник | документов | данные до | отставание |
|---|---|---|---|
| github | 250 | 2017-03-22 | 3462 дня |
| gdelt | 65 | 2024-11-26 | 656 дней |
| openalex | 400 | 2026-09-01 | 12 дней |

Технология, по которой GitHub не догрузился, выглядит как технология, в
которой прекратилась разработка. Ничто в системе этого не замечало.

**Что сделано:** `scripts/audit_coverage.py` заполняет
`source_coverage.coverage_end_date` по фактическим данным и предупреждает
об отставании. Поле было в схеме §32.1 с самого начала, но ничем не
заполнялось.

**Что требует внимания:** частичная загрузка допустима только с записью
реально покрытого диапазона. В production backfill должен либо доходить
до конца интервала, либо фиксировать, где он остановился.

## 11. Правило «missing ≠ zero» не покрывает пропущенные периоды

**ТЗ:** §24.19 требует не подменять нулём недоступную *метрику* и
перераспределять её вес.

**Пробел:** правило сформулировано для метрик, но не для времени. Если
источник перестал поставлять данные с какого-то месяца, все последующие
месяцы содержат ноль — и формулы §24.4/24.5 читают это как падение
активности. Отличить «искали и не нашли» от «не искали» по значению
невозможно.

Эффект измерен: до исправления Privacy-Preserving ML занимала 2-е место с
ETS 60.3, опираясь на research-балл, посчитанный по окну без покрытия.
После — технология честно помечена как не имеющая достаточных данных
(ETS 0, confidence 2.4) и из ранжирования исключена.

**Что сделано:** месяцы после `coverage_end_date` помечаются UNAVAILABLE,
а не заполняются нулями. Прирост по метрике считается, только если
покрыто не менее 75 % окна; иначе вес перераспределяется по §24.19.

**Формулировка для ТЗ:** правило §24.19 стоит расширить — «отсутствие
данных за период не эквивалентно нулевой активности за период».

## 12. Выдача GDELT на 77 % не по теме

**Замер на пилоте.** Запрос `"agentic AI"` к GDELT DOC 2.0 вернул из
30 статей 23 не относящиеся к предмету — биржевые подборки вида
«10 Best Nancy Pelosi Stocks to Buy in 2026».

Низкий вес источника (0.40 по §24.17) от этого не защищает: вес снижает
вклад *верного* сигнала, а не отсеивает неверный. Попав в
`news_mentions`, такие статьи напрямую искажают Market Momentum (§24.9).

**Что сделано:** проверка, что все значимые слова запроса присутствуют в
заголовке статьи. На реальной загрузке отброшено 335 записей из 400.

**Ограничение:** проверка строгая и отбрасывает статьи, где технология
упомянута только в теле. Для сигнала внимания это приемлемо; если
потребуется полнота, нужна классификация текста, а не фильтр по заголовку.
