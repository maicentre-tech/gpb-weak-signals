## 1. Как читать этот документ

Проект начинался под документ v1.4 — развёрнутую enterprise-интерпретацию задания.
После получения оригинального PDF Газпромбанк.Тех выяснилось, что это **хакатон с
жюри и live-защитой**, а не промышленное внедрение. Часть построенного попадает в
цель, часть оказалась преждевременной, а главное — **единственная объективная метрика
оценки (точность ≥80%) не закрыта вообще**.

Ниже: фактическое состояние, разрыв по каждому acceptance criterion и порядок работ.

## 4. P0 — блок ML-модели (AC-01, AC-02, AC-08)

Единственная объективная метрика хакатона. Ничего из этого пока не существует.

### 4.1. Аудит датасета

- Связь между стадией развития, трендом упоминаний и баллом.
- Дубликаты и почти-дубликаты технологий.
- Leakage audit: не утекает ли `Балл` через текстовое обоснование.
- Распределения признаков по шести областям.

### 4.2. Фиксация target

Решение принимается **до** подбора модели и не меняется после просмотра validation.
Варианты:

1. Бинарный: сигнал / не сигнал (нужен negative set).
2. Ordinal по баллу 3–7 + отдельное правило перевода в signal/non-signal.
3. Регрессия балла + порог.

Датасет содержит **только положительные примеры** — без решения по негативу
бинарная постановка невозможна.

### 4.3. Протокол отрицательных примеров

Самая рискованная часть: лёгкий негатив даёт завышенную метрику, и 80% перестают
что-либо доказывать.

| Класс негатива | Как строить | Проверка |
|---|---|---|
| Зрелые технологии | высокий объём + низкое ускорение + высокая maturity из собственного корпуса | должны быть реально зрелыми, а не просто известными |
| Маркетинговый хайп | высокий early warning при низком confirmed | механизм уже заложен в схеме v1.5 |
| Информационный шум | малый объём, низкая coherence, нет cross-source | не должен быть тривиально отделим |

Негатив строится **из того же корпуса**, а не из выдуманного списка. Отдельный
аудит: если модель отличает негатив по одним словам — метрика недействительна.

### 4.4. Модели и валидация

- Baseline: Logistic Regression — контрольная точка и прямая интерпретируемость.
- Дерево: Random Forest / Gradient Boosting.
- Основной кандидат: XGBoost по табличным признакам.
- Текст: multilingual embeddings (модель уже установлена).
- Обязательно: cross-validation, hold-out, ablation по группам признаков,
  калибровка, confusion matrix, PR-AUC, error analysis.

### 4.5. Интерпретация

SHAP для бустинга либо коэффициенты для линейной модели. В выдаче — 3–6 ключевых
факторов с направлением вклада, а не только итоговый процент.

## 5. P0 — открытый поиск без онтологии (AC-03)

Сейчас система находит только то, что вписано в `data/ontology/ai_pilot.json` — 18
технологий. Зарождающаяся технология по определению ещё не имеет названия в нашей
таксономии, поэтому **это прямое невыполнение требования ТЗ**, а не недоработка.

Минимально достаточно для MVP (полноценное расширение онтологии — P2):

1. Извлечение кандидатов из текстов найденных документов (терминология, именованные сущности, n-граммы с ростом частоты).
2. Семантическое объединение кандидатов через эмбеддинги.
3. Прогон объединённых кандидатов через ту же feature pipeline и модель.

## 6. P0 — русскоязычная выдача (AC-05)

Требование явное: аналитика на русском, для зарубежных источников — русское резюме
с сохранением оригинального названия, ссылки, даты и языка.

- Локальная модель для резюмирования уже работает.
- Нужно: поле `is_generated_summary`, сохранение `original_title`, пометка
  автоматического перевода.
- Claim verifier должен работать **по оригинальному тексту**, а резюме отдавать
  пользователю: иначе проверка чисел сломается на переводе.

## 7. P0 — Docker (AC-09)

Отдельный критерий оценки (§8.2 «успешность развёртывания по предоставленной
инструкции»). Нужно:

- `Dockerfile` для API, `docker-compose.yml` с PostgreSQL + pgvector + API + UI.
- Healthcheck и одна команда запуска.
- Раздел в README с командами.
- Фиксация зависимостей.
- Учесть ограничение ТЗ: демонстрация на ноутбуке, серверные мощности не предоставляются.

## 8. P1 — метаданные источников (AC-06)

В таблицу источников и выдачу добавить: `source_type`, `original_language`,
`trust_level`, `trust_reason`, `retrieved_at`, `is_generated_summary`,
`original_title`.

Правило из ТЗ: корпоративный блог, пресс-релиз, соцсеть или агрегатор **не могут
быть единственным основанием** для включения технологии. Нужен явный single-source
rule с логированием причины.

---

## 9. P1 — фильтры хайпа и шума (AC-07)

Maturity-фильтр есть. Не хватает:

- **Hype filter:** высокий early warning при низком confirmed → статус «возможный хайп».
- **Noise filter:** малый объём + низкая coherence + нет независимых источников → исключение.
- **Логирование исключений:** `candidate → filter → reason`, чтобы показать жюри
  отфильтрованную зрелую технологию и объяснить причину (пункты 7–8 demo-сценария).

## 10. Известные дефекты методологии

Найдены при работе с реальными данными, исправления внесены, но **каждый меняет
методику расчёта и требует согласования**. Подробно — в [limitations.md](limitations.md).

1. Формула growth §24.4 с `eps=1` не защищает от малых выборок: рост 0 → 3 документа даёт больший балл, чем 3 000 → 10 000.
2. Задержка индексации читается как спад активности.
3. Правило «missing ≠ zero» не покрывало пропущенные периоды внутри окна.
4. §9 не различает факт из источника и рассчитанный показатель.
5. Перераспределение весов ломает порог auto-accept при малом покрытии сигналов.
6. Шум GDELT: 77% выдачи по фразовому запросу не по теме.
7. 25% веса ETS не поддаётся историческому бэктесту с холодного старта.
8. `PRIMARY KEY` из §32.1 нереализуем в PostgreSQL.

## 11. Что отложено осознанно

Сильные идеи, не влияющие на критерии хакатона:

- Автоматическое расширение онтологии через HDBSCAN/BERTopic (P2).
- Ансамбль специализированных детекторов.
- Bayesian change-point detection.
- Learning-to-Rank после накопления разметки.
- Многоязыковая асимметрия как отдельный сигнал.
- Подключение EPO, CORDIS, PatentsView.
- Пять экранов экспертного ревью, существующих только в API.
